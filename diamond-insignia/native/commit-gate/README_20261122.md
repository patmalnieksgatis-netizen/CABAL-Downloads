# Diamond Insignia v291 — exactly-once native commit gate (2026-11-22)

**Status: C++17 source implemented, offline test PASS, NOT integrated or installed in WorldSvr.** This is strictly Diamond Insignia, NOT Mandarat.

## Production problem addressed

The prior isolated SQLite test host rejected client replays after a commit. A network retry could therefore show a failure even though the item and WExp were already charged. \`DiamondCommitGate\` uses an authenticated, account-locked, revision-keyed **persisted receipt** to return the original successful result after identical retries, without charging again. A different operation with the same revision is rejected.

Actual source:
- \`DiamondCommitGate.h\`, \`DiamondCommitGate.cpp\` in this folder.
- Header depends on the pre-existing \`diamond-insignia/native/diamond_abi.h\` and the already-tested \`libDiamondNative.so\` exported functions \`cabal_diamond_evaluate\` etc.

The gate:
1. Accepts an opaque WorldSvr-authenticated session; \`Backend::begin\` supplies trusted UserNum/CharacterIdx from a real session, begins a transaction, and holds an **exclusive account lock**. A user ID from a client packet is never trusted.
2. Looks up a committed receipt for \`(UserNum, expectedRevision)\` under lock. If command and mastery ID match, returns \`Replayed\` and prior result; otherwise \`RevisionConflict\`.
3. Loads trusted account-owned resources (WExp, verified item **33554961**, Platinum/Diamond state, slots, mastery levels).
4. Calls the native rules engine on the *actual 116,812-byte staged Diamond SCP*.
5. Permits \`Backend::commitAll\` only after the rules approve and the revision increases exactly once; the backend MUST persist inventory debit, WExp debit, progression, mastery and the receipt **inside a single durable transaction**. If the game only exposes asynchronous DBA cmd46/47, that guarantee is not available; a durable outbox/recovery mechanism is mandatory, and integration must fail closed until implemented.
6. Releases transaction/lock on all paths. No client success packet before durable commit.

The gate does **not** invent wire opcodes, S2C bytes, or unverified player-layout offsets. \`0x09F3\` remains an existing Merit Mastery command, \`0x0B10\` belongs to Platinum and is never usurped. Only Diamond Mastery IDs 159–474 are considered for the Diamond-specific action.

## Offline tests

Using the user-supplied real Diamond staged SCP and existing compiled native rules engine, local C++ synthetic backend tests PASS:
- Platinum→Diamond rank-up: WExp 40000→10000, tickets 120→20.
- Replayed successful rank returns same committed receipt without new debit.
- Different action with used revision is rejected.
- Simulated storage failure leaves account unchanged, and retry is permitted.
- Mastery 159 can be bought after rank-up.
- 8 concurrent requests with same revision: exactly one \`Applied\`, seven \`Replayed\`.
- Invalid Gold ID 158 is rejected.
- AddressSanitizer/UndefinedBehaviorSanitizer PASS.

**Caveat:** in-memory simulated backend only. This is NOT proof of actual MSSQL transaction durability, WorldSvr compatibility or any gameplay activation. Test sources and ELF-only staging materials are in conversation archive \`CABAL_v291_Diamond_CommitGate_20261122.zip\` (SHA256 \`c61f9b8370ef99dc8fd9904d365e6b3f5ba3a674c28c6d82351870646bd283b3\`). No private source tree or staged SCP was uploaded to public GitHub.

## Verified existing source facts to use for future integration

- Existing v14 EventPass owner reader contains userNum at \`USERDATACONTEXT+0x0890\` and characterIdx at \`+0x0A24\`. WorldSvr \`USERCONTEXT+0xE8\` provides data pointer, but these layout observations are not a substitute for authenticating the live session.
- Known Server01 tables from user-provided read-only SQL catalog: \`cabal_merit_table\`, \`cabal_merit_platinum_table\`, \`cabal_merit_platinum_mastery_table\`. The true Diamond varbinary codec, real inventory item debit and WExp persistence API remain unverified; never update those tables blindly.
- Prior deployments of patched lib.so and passive sidecar failed with \`exit 78\`; the sidecar rollback itself failed until the owner restored the historical disk config. The owner confirmed the game works afterward. **Do not install this gate, change LD_PRELOAD, replace lib.so, or restart the VM.**
